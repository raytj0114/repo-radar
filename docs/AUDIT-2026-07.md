#### W1: ブランチ保護の必須チェックに E2E (Playwright) が含まれていない

- **場所**: GitHubリポジトリ設定・ルールセット `protect-main`（id 19762153）。コードでは [.github/workflows/ci.yml:62](../.github/workflows/ci.yml) の `e2e` ジョブが対象
- **問題**: 必須status checkは `Lint / Typecheck / Test` と `Build` の2つのみ。`E2E (Playwright)` が赤でもPRはマージできる
- **なぜ問題か**: #12/#15/#17 で構築したE2E（375px横スクロール検知=不変条件7、並列化の回帰検知、認証必須画面のスモーク、外部通信ガード）が、**マージゲートとしては機能していない**。CI上に赤バツは出るが、見落とし・焦り・auto-mergeのいずれでも素通りできる。E2Eだけが検知できる回帰（下の実証プローブ a・c）がmainに入り得る、という意味で「形だけ」の穴に該当する
- **推奨する直し方**: ルールセット `protect-main` の `required_status_checks` に `E2E (Playwright)`（integration_id 15368 = GitHub Actions）を追加する。設定変更のみでコード変更は不要。E2Eジョブの所要（現状ローカル25秒+build、CIで数分）は必須化に耐える長さ

#### W2: レート上限の縮退表示（RATE_LIMITED分岐）を守るテストがユニット1層しかない

- **場所**: [src/app/(main)/repos/[owner]/[name]/page.tsx:47](<../src/app/(main)/repos/[owner]/[name]/page.tsx>)・[:57](<../src/app/(main)/repos/[owner]/[name]/page.tsx>)、[src/app/(main)/trending/page.tsx:51](<../src/app/(main)/trending/page.tsx>)、[src/app/(main)/page.tsx:76](<../src/app/(main)/page.tsx>)

#### N3: ルールセットが「ベースブランチ最新化」を要求していない

- **推奨する直し方**: 現状維持で構わない。並行PRが増えたら `strict` 化（Require branches to be up to date）を検討する

| 差分（許容）                                          | —                 | お気に入り判定のPrismaクエリが「メタ404でも実行される」ようになった（旧は404時スキップ）。追加コストはDB1クエリ。また「repo404 + Prisma障害」の複合時に旧はRepoNotFound・新はエラー画面になるが、DB障害を隠さない方向の差であり許容と判断              |

#### トレンド（#19）

| 項目                                                  | 判定     | 根拠                                                                                                                             |
| ----------------------------------------------------- | -------- | -------------------------------------------------------------------------------------------------------------------------------- |
| 検索がレート上限 → 縮退Notice（フィルタUIは表示継続） | **等価** | 旧try/catch→フラグ、新 `unwrapSettled`→番兵。JSX側の分岐は不変                                                                   |

#### 共通（client.ts の変更）

- revalidate値（releases 300 / repository 3600 / search 1800）は不変でスキルの表と一致
- `fetchReleases` のオプション化は既定値が旧定数（100×3）と同一のため、既存呼び出し（詳細ページ）の挙動は不変。上限・下限を関数側でクランプ（1〜100、1ページ以上）しており、呼び出し側の定数ミスにも安全
- 取得量の指定はサーバー側定数のみ（ダッシュボードの `RELEASES_PER_REPO`）。クライアント入力が `perPage`/`maxPages` に到達する経路はない（スキル「取得量の指定はサーバー側の定数だけで決める」に適合）

### Issue案 B: レート上限の縮退表示をE2Eで検証できるようにする

**背景**

GitHub APIレート上限時の縮退表示（ダッシュボード=部分Notice、詳細/トレンド=全面Notice）はARCHITECTURE.mdが定める仕様だが、E2Eモックは常に十分な残量を報告するためこの経路をテストが一度も踏まない。監査の実証プローブdで、`unwrapSettled` の番兵変換を壊してもユニットテスト1件しか落ちず、ページ側の分岐（`if (repo === RATE_LIMITED)` 等）を壊した場合は検知手段が無いことを確認した（docs/AUDIT-2026-07.md W2）。実ユーザーがレート上限に達した時に初めてエラー画面で発覚するリスクがある。

**変更対象**

- e2e/mock-github/server.mjs: 特定owner（例: `ratelimited` プレフィックス）への応答で `x-ratelimit-remaining` をフロア未満（core: 0）にする制御を追加
- e2e/constants.ts: 上記ownerの定数追加
- e2e/authed.spec.ts: 縮退表示の検証を追加（最低限、リポジトリ詳細で「レート上限に達したため」Noticeが表示されること）

**受け入れ条件**

- [ ] レート上限経路のE2Eが追加され、`npm run e2e` が緑
- [ ] ページ側のRATE_LIMITED分岐を意図的に削除するとE2Eが赤くなることを確認する（確認後復元）
- [ ] 既存のE2E（低残量を観測した後に実行される他テスト）が巻き込まれない
- [ ] 外部通信は発生しない（既存ガードの対象のまま）

**制約**

- `rateLimitRemaining` はアプリサーバーのプロセス内モジュール状態（src/lib/github/client.ts）。低残量を一度観測させると**同一プロセスの以降の全core呼び出しが遮断される**。テスト分離のため、(1) 縮退検証をworker順序に依存させない、(2) 検証後に高残量応答を踏ませて回復させる、(3) またはsearchプールのみで検証しcoreを汚さない、のいずれかの設計を必ず入れること
- モックの応答操作はサーバー側の環境変数/URL規約で行い、アプリコードには手を入れない（不変条件1・E2E方針と同じ原則）
