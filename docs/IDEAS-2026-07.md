# 機能案 2026-07 — 「毎日開きたくなる理由」を作る

コードベース全体の調査に基づく機能提案。採用が決まったものだけIssue化する。

## 前提: この資産があるから安い、という話

案の評価に使った、このアプリ固有の資産:

1. **`ReleaseSummary` は全ユーザー共有・TTLなしの要約プール**
   `userId` を持たず、cacheKey（`owner/repo@tagName`）でユニーク。リリースは不変なので
   一度生成した日本語3行要約は永久に有効。つまり要約は「使い捨ての表示物」ではなく
   **合成可能な部品**として貯まり続けている。これを横断・積み上げて使う機能は、
   他所でゼロから作ると要約生成コストが毎回かかるが、ここでは限界コストほぼゼロ。
2. **GitHub API 5,000req/h のサーバーPAT枠がほぼ遊んでいる**
   現状の消費はページ表示時のオンデマンド取得（5分キャッシュ付き）と1日1回のcronのみ。
3. **ダイジェストの基盤一式**（cron + CRON_SECRET検証 + cacheKey規約 + `DailyDigest` テーブル + 画面）が完成済み。

あわせて、調査で見つけた構造上の負債（案1で同時に解消できる）:

- **(a)** `src/lib/digest.ts` はダイジェスト生成時に GitHub の生 `release.body` を再取得して
  LLM に入れており、既に `ReleaseSummary` にある同一リリースの要約を再利用していない
- **(b)** その結果、ダイジェストの AI 呼び出しは「その日リリースがあった**ユーザー数**」に
  比例している（`digest.ts:8-9` が自認）。不変条件2の精神と唯一矛盾する箇所
- **(c)** cron が 21:00 UTC 実行なのに「UTC 当日の `published_at`」でリリースを抽出するため、
  **21:00〜24:00 UTC に公開されたリリースは永久にどのダイジェストにも載らない**

## 案1: ダイジェストの「朝刊」化 — 共有要約の組み立てに置き換える

### 何をするか

現在のダイジェストは「ユーザーごとに1回、生のリリースノートを LLM に投げた1枚のテキスト塊」。
これを **「リリースごとの共有3行要約（`ReleaseSummary`）を組み立てた、リンク付きの朝刊」** に置き換える。

- cron はまず当日の新規リリースを**全ユーザー横断で重複排除**し、未要約のものだけ
  `ReleaseSummary` に生成・保存する（= AI呼び出しは新規リリース数にのみ比例）
- 各ユーザーのダイジェストは、そのユーザーのお気に入りに該当する要約を**組み立てるだけ**
  （LLM 呼び出しなし）。冒頭の総括は「3リポジトリ・5リリース（うち破壊的変更1件）」のような
  ルールベース生成で足りる
- 画面は `whitespace-pre-line` のテキスト塊から、リポジトリ詳細へのリンク付きカードの一覧へ
- 収集ウィンドウを「UTC 当日」から「前回cron実行時刻〜今回実行時刻（前日21:00〜当日21:00 UTC）」に
  変え、負債(c)の取りこぼしを解消する

### 「これ欲しかった」場面

朝6時、通勤前にスマホで `/digest` を開く。昨夜 Next.js と Prisma がリリースを出していて、
それぞれ3行の日本語要約が**既に生成済み**で並んでおり、気になった方をタップすると詳細に飛べる。
「ボタンを押して要約を待つ」工程がゼロ。これが毎朝続くと、開かない日は「見逃した」気分になる。

### なぜこのアプリなら安いか

要約プールが共有・不変だから、100人が同じ `vercel/next.js` をお気に入りにしていても
生成は1回。汎用のニュースレターサービスでこれをやると購読者ごとに要約を作るか、
配信側で要約基盤を丸ごと持つことになる。ここでは既にある部品を並べ替えるだけ。
副産物として、cron が生成した要約はリポジトリ詳細画面の「AI要約を表示」でも即ヒットする
（プレウォーム効果）。

### 実装スケッチ

- `prisma/schema.prisma`: `DailyDigest` に `entries Json?` を追加（`content` は旧データ表示用に残す）。
  `prisma migrate dev` 必須
- `src/lib/digest.ts`: ①窓関数を `(前日21:00, 当日21:00]` に変更 ②全ユーザーの当日リリースを
  cacheKey で dedupe → 未要約のみ `generateText`（既存の `summaries.ts` の生成部を共通関数に抽出して再利用）
  ③ユーザーごとの組み立ては純関数化してユニットテスト
- `src/app/(main)/digest/page.tsx`: entries があればカード表示、なければ従来表示。375px確認（不変条件7）
- テスト: `tests/digest.test.ts` の窓関数・dedupe・「同一リリースを持つ2ユーザーで生成1回」を追加。
  `e2e/authed.spec.ts` のダイジェスト節とシードを更新

**注意**: ボディが空のリリースは従来どおり要約せず「リリースノートなし」としてリンクのみ載せる。
検知の即時化（15分ポーリング等）は Vercel Hobby の cron が日次粒度のため今回は見送り
（必要になったら GitHub Actions の schedule から CRON_SECRET 付きで叩く手がある）。

### 見積もり

コスト: **2〜3日**（マイグレーション + cron改修 + 画面 + テスト/E2E）。
インパクト: **大**。「毎日開く理由」の本丸で、同時に負債(a)(b)(c)を全部返せる。

## 案2: キャッチアップ・ビュー — 「自分のバージョンから今まで」を一気読み

### 何をするか

リポジトリ詳細に「このバージョンから読む」を追加する。過去のタグを1つ選ぶと、
そのタグの次〜最新までの全リリースの3行要約を**時系列に積み上げて**1画面で読める。
URL は `/repos/[owner]/[name]?from=v1.2.3` にしてチームに共有可能にする。

- 範囲内で未生成の要約はその場で生成する。ただし1回の操作で生成するのは最大10件などに
  キャップし、超過分は「続きを生成」で明示的に進める（コスト暴走の防止。生成済み分は
  即表示されるので体感は軽い）
- 範囲のロールアップ要約（LLMでさらに1段まとめる）は**やらない**。3行×N件の積み上げで
  十分読めるし、範囲キー（`owner/repo@from..to`）はタグの組み合わせ分だけ生成されうるので
  会計が濁る

### 「これ欲しかった」場面

半年放置していたプロジェクトの Next.js を 15.1 から 16.2 に上げたい。GitHub のリリース
ページだと英語の長文リリースノートを12個分スクロールして読むことになる。ここでは
`?from=v15.1.0` を開けば、その間の12リリースが日本語3行×12で数分で読み切れて、
どこで破壊的変更が入ったかも一目でわかる（案3導入後はバッジ付き）。

### なぜこのアプリなら安いか

これは**要約が「リリース不変・共有・無期限」で貯まっているからこそ成立する機能**。
人気リポジトリほど他ユーザーの閲覧で要約が既に埋まっており、開いた瞬間にほぼ全件表示される。
同じものを汎用 AI チャットでやると毎回全リリースノートを読み直す（入力トークンが範囲の
全文に比例する）。ここでは新規生成分しか払わない。GitHub UI にも RSS にもこの「区間を
要約で読む」体験は存在しない。

### 実装スケッチ

- `src/app/(main)/repos/[owner]/[name]/page.tsx`: `searchParams.from` を受け、既存の
  `fetchReleases`（既定で最大300件取得済み）から範囲をスライス。タグ選択 UI を追加
- 新 Server Action `getCatchUpSummaries`（`src/app/actions/summaries.ts` に追加）:
  `requireSession` → 入力は owner/name/fromTag のみ（既存 `releaseSummaryInputSchema` の部品を再利用）→
  範囲の cacheKey を一括 `findMany` → 未生成分を上限付きで順次生成。生成部は案1で抽出する
  共通関数を使う
- スキーマ変更: **なし**（cacheKey 体系そのまま）
- テスト: 範囲スライスの純関数、キャップ動作、キャッシュヒット時に Gemini を呼ばないこと

**不変条件チェック**: 生成トリガーはユーザー操作だが、キャッシュは共有かつリリース単位なので
呼び出し総数は「未要約リリース数」で頭打ち。キャップが1操作あたりの burst を抑える。
`from` はタグ名として既存の Zod パターンで検証し、プロンプトには入れない（本文はサーバー取得）。

### 見積もり

コスト: **1〜2日**（スキーマ変更なし、既存部品の組み合わせ）。
インパクト: **大**。エピソード的（毎日ではなく「上げるとき」）だが、「このアプリでしか
できない」度は全案中で最高。ブックマークされる理由になる。

## 案3: 破壊的変更レーダー — 要約を構造化して「壊れるか」を一目に

### 何をするか

Gemini の出力をプレーンテキスト3行から構造化 JSON（`{ lines: string[], hasBreaking: boolean,
breakingNote?: string }`）に変え、`ReleaseSummary` に `hasBreaking` / `highlights` / `promptVersion`
を追加する。以後に生成される要約すべてに「破壊的変更あり」の判定が付き、

- ダッシュボードのタイムラインに ⚠ バッジ
- 案1の朝刊で破壊的変更を先頭に集約（「今朝の破壊的変更: 2件」）
- 案2のキャッチアップで「破壊的変更だけ表示」フィルタ

が可能になる。既存キャッシュ行は構造なしのまま従来表示（`promptVersion` で区別でき、
再生成は将来の管理者操作に委ねる。TTLなし運用でプロンプトを進化させるための世代管理は
どのみち必要になる列)。

### 「これ欲しかった」場面

朝、依存を上げる予定はないが「今日どこかで何か壊れるものが出たか」だけは知っておきたい。
ダッシュボードを開いて ⚠ が無ければ3秒で閉じる。あれば該当リリースだけ読む。
「全部読む」ではなく「読むべきものだけ教えてくれる」への転換で、毎日の確認コストが
数分→数秒になる。

### なぜこのアプリなら安いか

分類は要約生成と**同一の1回の呼び出し**で済み、AI呼び出し回数は1回も増えない。
判定結果は共有プールに永久保存されるので、全ユーザーの全画面がタダで恩恵を受ける。
リリースノートから breaking change を機械抽出するのは Renovate 等でも不完全な難題で、
LLM 前提の本アプリだから素直に解ける。

### 実装スケッチ

- `src/lib/gemini/client.ts`: `generationConfig` に `responseMimeType: 'application/json'` +
  `responseSchema` を追加した構造化版を用意（エンベロープの Zod 検証は既存を踏襲、
  中身も Zod でパース。パース失敗はリトライ→最終的にテキストのみで縮退保存）
- `src/lib/gemini/prompts.ts`: 判定基準（API削除・デフォルト変更・要マイグレーション等）を明記
- `prisma/schema.prisma`: `hasBreaking Boolean?` / `highlights Json?` / `promptVersion Int @default(1)`。
  migrate 必須
- UI: `release-summary.tsx`、ダッシュボードのタイムライン項目、（導入後）digest カードにバッジ
- テスト: 構造化パースの正常/縮退、プロンプト、バッジ表示。ai-cost-guard スキル遵守

### 見積もり

コスト: **2〜3日**（出力形式の移行が本体。UI は小さい）。
インパクト: **中〜大**。単独でも効くが、真価は案1・2の表示品質を底上げする下地であること。
先に入れると案1・2が最初から ⚠ 付きで出せる。

## 案4: スタック・インポート — package.json を貼ると「自分のレーダー」になる

### 何をするか

お気に入り管理ページ（未実装・前提化OKとのこと）に「package.json から一括登録」を追加する。
テキストエリアに package.json を貼ると、サーバーが npm レジストリで各依存の GitHub リポジトリを
解決し、候補一覧をチェックボックスで確認 → 一括で `addFavorite`（既存 upsert で冪等）。
あわせて依存のバージョン指定を `FavoriteRepo.trackedVersion` として任意保存し、
案2のキャッチアップに「あなたの v15.1 から」を自動プリフィルする。

### 「これ欲しかった」場面

新規ユーザー（または新プロジェクト開始時）が、依存30個を1つずつ検索して星を押す代わりに、
package.json を貼って30秒で追跡開始。翌朝から朝刊（案1）が「自分が実際に使っているもの」
だけで届く。汎用トラッカーが「自分の道具箱のレーダー」に変わる瞬間で、リテンションの入口。

### なぜこのアプリなら安いか

LLM 呼び出しは**ゼロ**。お気に入りの upsert・入力検証（`favorite-input.ts`）・詳細画面は全部
既存で、追加するのは「npm パッケージ名 → GitHub owner/name」の解決だけ。Dependabot/Renovate は
バージョン更新の PR は作るが「何が変わったかを日本語で読む」体験は無く、そこは案1・2が受け持つ。

### 実装スケッチ

- 新 Server Action `resolveDependencies`: `requireSession` → 入力 Zod（依存名の形式検証・上限200件）→
  `https://registry.npmjs.org/{pkg}`（`latest` の `repository.url`）を並列数制限付きで取得 →
  GitHub owner/name に正規化して候補を返す。レジストリ応答は `next: { revalidate: 604800 }` で
  キャッシュ（パッケージ→リポジトリ対応はほぼ不変）
- **新規外部API**: npm レジストリ。`env.ts` に `NPM_REGISTRY_BASE_URL`（既定値付き）を追加して
  E2E でモック可能にし、`.env.example` と ARCHITECTURE のデータフロー図を同時更新（不変条件3）
- `prisma/schema.prisma`: `trackedVersion String?` を追加（migrate）
- エッジケース: `repository` フィールド欠落 / monorepo（`directory` 指定）/ scoped package。
  解決不能なものは「手動で検索」への導線に落とす
- テスト: 解決ロジックの純関数部、Server Action の認証・上限、E2E はボタン起点なのでスモーク外可

### 見積もり

コスト: **3日**（外部API追加の作法と正規化のエッジケースが本体）。
インパクト: **中〜大**。毎日開く理由そのものではなく、案1・2を「自分ごと」にする増幅装置。
お気に入り管理ページを作るタイミングに同乗させると安い。

## 検討して捨てた案

### 1. スター推移グラフ / アクティビティ可視化

ARCHITECTURE のコンセプト行に「スター推移」とあるが捨てた。定期スナップショット収集の
インフラ（cron + 履歴テーブル）を新設して得られるのが「たまに眺めるグラフ」で、
star-history.com 等の既存サービスで代替可能。要約プールという固有資産を1ミリも使わず、
「よくあるダッシュボード機能」の典型なので狙わない。

### 2. Slack / メール / プッシュ通知への配信

ROADMAP が明示的にスコープ外としている（Webhook・リアルタイム通知）ことに加え、
今回のゴールと逆向き。通知は「アプリを開かなくて済む」方向の最適化であり、
「毎日開きたくなる」を作る前に外へ配ると開く理由が消える。配信基盤（到達性・購読管理・
失敗リトライ）は高コストで、この資産群が安くしてくれる部分がどこにもない。

### 3. 要約のパーソナライズ（ユーザーの文脈に合わせた要約・対話）

「自分のコードに影響ある?」と聞ける対話や、ユーザーの関心に合わせた要約の書き分けは
魅力的に見えるが、出力がユーザー依存になった瞬間に **共有キャッシュが成立しなくなり、
AI呼び出しが ユーザー数 × コンテンツ数 に比例する**。このアプリのコストモデル全体が
「要約はユーザー非依存」に立脚しており、不変条件2と正面衝突する。クライアント入力を
プロンプトに入れない規約とも矛盾する。パーソナライズは「何を要約するか」（お気に入り、
案4のスタック）で実現し、「どう要約するか」は共有のまま守る、が本アプリの解。

# 第二部 — 制約を外して: 「毎朝、眺めたくなる」ためだけの5方向

（2026-07-30 追記。第一部へのフィードバックを受けた再考）

## 前提の置き直し

このアプリは製品ではなく、**作者個人の道具であり作品**である。評価軸はただ一つ、
「作った本人が、毎朝これを開いて眺めたくなるか」。

第一部の制約はすべて破棄する。GitHubのUIと重なっても、実装が長くても、テーマが
リリース追跡から離れても構わない。残す制約は一点のみ:
**AI呼び出しがユーザー数に比例しないこと**（財布のため）。

## この5案は全部盛りできない

案1〜3は、それぞれがアプリの**顔**——アートディレクション、既定画面、体の構え——を
丸ごと要求する。

| 案        | 画面                 | 構え             | 時間感覚             |
| --------- | -------------------- | ---------------- | -------------------- |
| 1. 管制室 | 暗い・燐光・動き続く | 周辺視で「掃く」 | 8秒（一掃引）        |
| 2. 文芸版 | 紙・静止・組版       | 熟読で「読む」   | 15分（一面）         |
| 3. 温室   | ガラス・光・生き物   | 愛着で「見守る」 | 数週間（開花と枯死） |

暗い管制室と生成りの紙面と朝日の温室は、同じアプリの中で同格には並べない。
どれを選んでも**それがRepoRadarの人格になる**。案4（深夜放送）はさらにモダリティごと
衝突する——「最良のセッションは画面を一度も見ないこと」と主張するから。
案5（考古学）だけは例外で、案1か案3の中に「部屋」として同居できる（後述）。

推す順: **管制室 → 文芸版 → 温室 → 深夜放送 → 考古学**。

---

## 案1: 管制室 — 名が体を表すまで

**【データ追加ゼロ枠】新しいデータを一切増やさず、見せ方だけで別物にする案。**

### 開いたとき、何が見えるか

消灯した部屋にCRTが一台。画面いっぱいの円形スコープ（PPI）。中心は自分。
燐光の緑の輝線が8秒で一周している。

お気に入りの各リポジトリは**輝点**として散らばる。中心からの距離は
「最終リリースからの経過時間」の対数——24時間以内なら最内リング、1年沈黙なら外周。
方位はリポジトリ名から決まる固定角。だから毎朝同じ場所に同じ機影がいて、
数週間で「右上の一群はReact系」と体が覚える。星座は暗記するものではなく、
通ううちに覚わるもの。

### 何が動くか

- 輝線が通過するたび輝点が発光し、次の一周までゆっくり燐光が減衰する
- 前回訪問以降にリリースした機影はひときわ明るく、短い尾を引き、脇にタグ名
  （`v16.2.0`）がトランスポンダコードのように刻印される
- 掃引が機影に当たるたび、下部のリードアウトに呼出符号（`vercel/next.js`）、タグ、
  経過時間、そして**キャッシュ済みの3行要約**がテレタイプのように1文字ずつ打たれる
- 外周ではトレンドの新顔が「未識別機」としてノイズ状に明滅する。勢いが続けば
  数日かけて内側へ滲み、消えれば消える
- 右上に SIGNAL（API残量 4,812/5,000）。操作は不要。ただ回っている。
  カーソルを機影に載せたときだけ識別票（要約カード）が開く

### AIの財布

ゼロ。ダッシュボードとトレンドが今日すでに取得しているデータと、
既存の要約キャッシュだけで全部描ける。

### これができたら嬉しい理由

名前の約束がようやく果たされる。「昨夜、自分の世界で何か動いたか」への答えが
一掃引8秒の周辺視で得られて、リストを読み下す往復がなくなる。

そして最大の発明は**静けさが見える**こと。輝点がゆっくり外周へ流れていくのは、
依存がメンテされなくなっていく姿そのもので、リストUIでは絶対に見えない。
モニタの隅に常駐させて仕事をし、視界の端で何かが光ったときだけ目をやる——
これは道具というより**計器**であり、計器は眺めるために存在する。

## 案2: 文芸版 — 日刊 RepoRadar

### 開いたとき、何が見えるか

画面は紙。生成りの地に墨の文字、差し色は朱の一色だけ。題字
「**日刊 RepoRadar 第413号** 2026年7月30日（木） 観測所発行」。

一面トップは昨夜いちばん大きかったリリースで、AIが見出しと前文を書く——
「**Next.js 16.2、キャッシュの既定を静かに反転** 移行は一行、影響は全域」。
本文は3段組・両端揃え・行頭ドロップキャップ。リリースノート原文からの引用は
罫で囲む。中段に短信欄（小さなリリースは1行記事）。下段にコラム「観測手記」——
AIが昨日のリリースノートの片隅からひとつ拾って書く400字。

紙面の隅に天気欄「本日のAPI残量: 晴 4,812」、スター相場欄（トレンドの騰落を
株式面の組みで、8ポイントの数字がびっしり）。最終面は連載「依存の系譜」——
毎日、お気に入りの中からひとつ、そのリポジトリの来歴を1回読み切りで。

### 何が動くか

ほぼ何も動かない。**それがこの案の主張**。朝6時に紙面が組み直される、それだけ。
印刷CSSを持ち、本当に刷って通勤電車で読める。動くのは号数だけ——それが増えて
いくことが、この道具と自分の連続性になる。

### AIの財布

見出し+前文はリリースごとに1回（不変・永続キャッシュ）。コラムは日に1本。
連載はリポジトリごとに1回書けば永久に再掲できる。すべてコンテンツ数比例。

### これができたら嬉しい理由

リリースが「消化すべき通知」から「読みたい記事」になる。そして使ってみれば、
要約より**見出し**のほうが毎朝の快楽になるはず——「うまいこと言うな」と朝一で
思わされる体験は、通知バッジからは絶対に生まれない。

これは第一部・案1（朝刊化）の配管をそのまま使った**過激形**でもある。
同じデータ、同じcron、魂だけ別物。堅実な案1を実装した先に、この紙面が待っている。

## 案3: 温室 — 依存の庭

### 開いたとき、何が見えるか

ガラスの温室。光は実時間と連動していて、朝6時なら朝の斜光、夜ならランプの灯。
棚にお気に入りの数だけ鉢が並び、各リポジトリはひとつの**植物種**。姿はリポジトリ名
から決定論的に生成され（枝ぶりのパラメータはハッシュ、葉形は言語に由来——
TypeScriptは広葉、Rustは多肉）、同じリポジトリは誰の温室でも同じ種になる。

- リリースのたびに一節伸びる。安定したリリースサイクルは健康な樹形を作る
- メジャーバージョンは**開花**し、一週間ほど咲き続ける（花色は言語色）
- 破壊的変更を含む花には棘が見える
- 半年リリースがなければ葉の彩度が落ち、一年で苔むして**石化**する。枯木は棚に残る
- ガラスの外には野の花（トレンド）が生えては翌週に消える。気に入ったものは
  鉢上げ（お気に入り登録）できる

### 何が動くか

葉が揺れる。ガラスが結露する。成長は訪問と訪問のあいだに起きるので、上流が
忙しかった翌朝は目に見えて伸びている。鉢を選ぶと**年輪ビュー**——同心円の
リリース輪に、キャッシュ済みの3行要約がラベルとして刻まれている。
切り株の年輪を読むように、プロジェクトの歴史を読む。

### AIの財布

ゼロ。植物の生成は決定論的なプロシージャルコードで、年輪ラベルは既存キャッシュの
再掲。

### これができたら嬉しい理由

依存を「追う」対象から「**育ちを見守る**」対象に変える。監査のときに突然
「これ2年更新されてない!」と気づく代わりに、毎朝すこしずつ枯れていくのを見る——
罪悪感ではなく季節として。メンテナンス履歴という最も無味乾燥なデータが、
庭という時間の器に変わる。そして枯れた鉢を手放す（お気に入り解除）ことにすら、
ささやかな儀式が生まれる。

## 案4: 深夜放送 — RepoRadar Radio

**【やりすぎ枠】普通のプロダクトレビューなら却下される案。**

### 開いたとき、何が見えるか

画面はウォールナット筐体のラジオチューナー。周波数ダイヤル、VUメーター、
ニキシー管の局名表示。それだけ。

電源を入れると6:00の**定時放送**——オープニングのジングル、アナウンサー（合成音声）が
昨夜のリリースを読み上げる5分番組。原稿はキャッシュ済み要約から日に1本生成され、
セグメントのあいだには空電ノイズが挟まる。天気コーナーはAPI残量。コーヒーを
淹れながら聴く。画面は見なくていい。VUメーターが声に合わせて振れているだけ。

ダイヤルを回すと**深夜便**。低いトーンの別人格が、ソフトウェア史の名リリースを
ひとつ選び、当時の文脈ごとリリースノートを朗読する——「1998年、Mozillaがソースを
開いた夜の話をしましょう」。1話生成すれば永久にアーカイブされ、毎晩1話ずつ増える。

お気に入りに破壊的変更が出た瞬間は、音楽がダッキングしてテレタイプ音、
臨時ニュースの声が割り込む。

### 何が動くか

針。VUメーター。ダイヤルの灯。あとは全部、音。

### AIの財布

原稿は日に1本、深夜便は1話につき生成1回（永久アーカイブ）、TTSも同じ会計。
コンテンツ数（日数・話数）に比例し、ユーザー数には比例しない。

### 普通のレビューなら却下される理由

リリーストラッカーが音声パイプラインと架空のラジオ人格とジングル制作を抱える。
工数は説明不能、価値は定量不能、「誰が頼んだ?」に答えがない。

### これができたら嬉しい理由

だからいい。朝の儀式が**目を要求しなくなり**、髭を剃りながら自分の依存の動静が
耳に入る。深夜便はソフトウェア史を寝物語に変える。そして人格がいると、道具が
「確認する対象」から「そこにいる相手」になる——作品としてのやりすぎは、
道具としての節度からは絶対に生まれない。

## 案5: 考古学 — 十年を三分で

### 開いたとき、何が見えるか

リポジトリをひとつ選ぶと画面が暗転し、タイトルが出る——
「**vercel/next.js 2016–2026 十年を三分で**」。

横に流れる時間の川。スター数が地形の標高としてせり上がっていき、リリースタグが
光のパルスで打たれ、メジャーバージョンは**石碑**として立つ。章の変わり目で
タイトルカード——「第三紀: App Router動乱（2023–2024）」。時代ごとの梗概はAIが
書く。再生が現在に到達すると、静かにライブ画面（管制室なり温室なり）へ引き継がれる
——「そして、いまここ」。

### 何が動くか

全部。これは眺める画面ではなく**上映される**画面。

### AIの財布

時代梗概は（リポジトリ × 時代）ごとに1回、不変・永続キャッシュ。
リリースは不変なので過去の章が書き換わることはない。第一部と同じ会計。

### これができたら嬉しい理由

新しい依存を「READMEを読んで」ではなく「**ドキュメンタリーを観て**」採用できる。
「このプロジェクトは二度の書き直しを生き延びた」という体感的な履歴は、どの解説記事も
与えてくれない。そして何も新着がない朝のための画面でもある——今日は動きがない、
だから古典を一本観る。

5案の中で唯一、他と両立する。管制室なら「記録再生モード」、温室なら「植物図鑑の
生育記録」として同居でき、文芸版なら連載記事として毎日1章ずつ**紙面に**載る。
