**数値の読み方（重要）**: 同じ計測結果の中に時間軸の違う2種類の数値がある。

- **シミュレート値**: 表とヘッダ行の Performance / LCP / FCP / Speed Index / TBT。Lighthouseがモバイル回線・CPU 4倍遅を
  Lantern で再現した推定値
- **観測値**: 各節の「内訳」やネットワーク時刻（TTFB、ドキュメント完了時刻、画像リクエストの時刻）。
  スロットリングを掛けない実測のトレース上の時刻

**この2つは時間軸が違うので足し引き・大小比較をしてはいけない。** 例として `/trending` の LCP は
シミュレート 1.9 s に対し観測 1.33 s。以下の各節では、内訳やネットワーク時刻は「観測値」と明示する。

#### 2026-07-28 の `/` 再計測（Issue #5 適用後）

ベースライン（2026-07-26）との比較: Performance 100 → 99、**LCP 1.9 s → 1.7 s**、CLS 0.001 → 0、TBT 30 ms 据え置き。
その他の値: FCP 0.9 s / Speed Index 3.0 s / TTFB 13 ms（観測値）/ 総転送量 180 KiB。

**スコアが 1 点下がった要因は Speed Index のみ。** LCP 1.7 s・TBT 30 ms・CLS 0・FCP 0.9 s はいずれも満点域で、
減点が入りうるのは Speed Index 3.0 s（重み10%）だけである。これはストリーミングのトレードオフそのもので、
シェルを先に出すぶん LCP は改善する一方、後追いで届くタイムラインが埋まるまで視覚的な完成は遅れる。
LCP と SI のどちらを取るかの判断材料として残す。

ストリーミングが効いていることがトレース上で確認できる（以下いずれも観測値）。

- **LCP要素が `h1`「ダッシュボード」**（シェル）になっている。LCPの内訳は TTFB 19 ms + Element render delay 402 ms
  ＝観測LCPは約 0.42 s で、リリース取得の完了を待っていない
- **HTMLドキュメントのレスポンスは 2.19 s まで開いたまま**なのに、そのシェルは 0.42 s の時点で描画を終えている
  （FCP ≤ LCP なので最初のペイントはさらに早い）。シェルを先に流し、タイムラインを後から同一レスポンスで送っている証拠
- タイムライン内のアバター画像リクエストが 2.33 s に発生しており、後追いで届いたコンテンツから発火している

注意: この計測は拡張機能が有効なプロファイルで実施した（Lighthouseの3rd party内訳に chrome-extension 由来で主スレッド計約 14 ms）。
2026-07-26 のベースラインは拡張機能を削除したクリーンなプロファイルのため、条件は完全には揃っていない。
ただし影響は主スレッド 14 ms 程度で、後述の「参考値」の例（拡張由来で TBT +300 ms）のような大きさではない。

#### 2026-07-28 の `/trending` 再計測（Issue #6 適用後）

ベースライン（2026-07-26）との比較: **Performance 99 → 100**、**LCP 2.1 s → 1.9 s**、CLS 0.001 → 0、TBT 30 ms 据え置き。
その他の値: FCP 1.0 s / Speed Index 1.9 s / TTFB 13 ms（観測値）/ 総転送量 221 KiB / リクエスト 72件（うち画像23件）。

トレースから読み取れること（以下いずれも観測値）。

- **TTFB は 13 ms だがHTMLドキュメントの完了は 1.28 s**。トレンドはページ内 `<Suspense>` を持たないため、
  ストリーミングの途中でデータ取得（GitHub検索 + お気に入り）の完了を待っている。並列化の効果はこの区間に含まれる
- **LCP要素は見出し下の説明文 `p`**「直近30日に作成された…」で、内訳は TTFB 15 ms + Element render delay 1.31 s
  ＝観測LCPは 1.33 s。ドキュメント完了（1.28 s）の直後であり、LCP はほぼデータ取得の完了待ちで決まっている
- 単発のラボ計測では GitHub検索APIの応答時間のばらつきの方が並列化の短縮幅より大きいため、
  この 0.2 s の改善を並列化の効果と断定はできない。並列化の直接的な効果測定は下記「詳細/トレンドページの逐次fetch並列化」の実測表を参照

観察: トレンドはシェルを先に送れていないため、ダッシュボードと同じ `<Suspense>` 化をすれば LCP をさらに縮められる余地がある（未着手）。

注意: この計測も拡張機能が有効なプロファイル（3rd party内訳の chrome-extension 由来は主スレッド計約 14 ms）。
ベースラインとの条件差は `/` の再計測と同じ扱い。

参考値（2026-07-26・拡張機能あり）:

| URL         | 画面     | Performance | LCP   | CLS | TBT    | 備考                                                     |
| ----------- | -------- | ----------- | ----- | --- | ------ | -------------------------------------------------------- |
| `/trending` | トレンド | 82          | 2.1 s | 0   | 640 ms | TBTのうち約300msは拡張機能（DeepL）由来の長タスク        |
| `/login`    | ログイン | 90          | 1.7 s | 0   | 20 ms  | Speed Index 13.0 sの異常値は拡張由来でスコアを押し下げた |

初回計測は拡張機能が有効な通常プロファイルで行ったため、Lighthouseが「Chrome拡張がページ読み込みに悪影響」と警告した。拡張機能を削除して再計測した結果が上のベースライン表であり、参考値の表はベースラインとしては使わない。

## 改善記録

### ダッシュボードのストリーミング化とリリース取得の軽量化（Issue #5）— 2026-07-27

**変更内容**

1. ダッシュボードのシェル（見出し）を即時送出し、タイムラインを `<Suspense>` の内側へ移した（フォールバックはスケルトン）
2. ダッシュボードのリリース取得を `per_page=5` の1ページのみに変更（リポジトリ詳細の全件取得は現状維持）

**GitHub API 取得量（1リポジトリあたり、実測）**

- 変更前: `per_page=100` を `Link: rel="next"` で最大3ページ辿る（最大300件）
- 変更後: `per_page=5` の1ページのみ（ダッシュボードの表示上限は1リポジトリ5件）

| リポジトリ     | 変更前                     | 変更後                 | 本文バイト数の削減 |
| -------------- | -------------------------- | ---------------------- | ------------------ |
| vercel/next.js | 3 req / 300件 / 907.7 KiB  | 1 req / 5件 / 15.0 KiB | -98.3%             |
| facebook/react | 2 req / 132件 / 888.4 KiB  | 1 req / 5件 / 10.1 KiB | -98.9%             |
| prisma/prisma  | 3 req / 248件 / 1719.1 KiB | 1 req / 5件 / 36.1 KiB | -97.9%             |

お気に入り10件のダッシュボード1回表示に換算すると、リクエスト数は約27回 → 10回、
転送量（非圧縮の本文）は約11.4 MiB → 約204 KiB になる（上記3リポジトリの平均から外挿）。

計測条件: 2026-07-27、公開エンドポイントへ未認証でリクエストし、レスポンス本文（非圧縮）の
バイト数を測った。`Link: rel="next"` が途切れる場合は実際のページ数がアプリの上限3より
少なくなる（facebook/react の 2 req はこのケース）。同じ数値は次のコマンドで再現できる。

```bash
# 変更前相当（最大3ページ）。rel="next" が無くなったら以降のページは発生しない
for page in 1 2 3; do curl -sS -w '%{size_download}\n' -o /dev/null \
  "https://api.github.com/repos/vercel/next.js/releases?per_page=100&page=$page"; done
# 変更後相当（1ページのみ）
curl -sS -w '%{size_download}\n' -o /dev/null \
  "https://api.github.com/repos/vercel/next.js/releases?per_page=5"
```

**シェル先行描画の確認**

初回レスポンスのHTMLが「見出し → スケルトン → 後追いのリリース本体」の順で届くことを
E2E（`e2e/authed.spec.ts` の「シェルはリリース取得を待たずに先に送出される」）で自動検証している。
描画タイミングではなくバイト列の順序を見るため、モックの応答が速くてもすり抜けない。
E2Eのシードはお気に入り10件（`e2e/constants.ts`）。

**本番での再計測**

2026-07-28 に本番 `/` を手動計測済み。LCP 1.9 s → 1.7 s、CLS 0.001 → 0。
数値と読み取りは上の「2026-07-28 の `/` 再計測（Issue #5 適用後）」を参照。

### 詳細/トレンドページの逐次fetch並列化（Issue #6）— 2026-07-28

**変更内容**

1. リポジトリ詳細: リポジトリメタ・リリース一覧・お気に入り判定（Prisma）を `Promise.all` で同時に投げる
   （従来はメタ → リリース → お気に入りの3段直列）
2. トレンド: トレンド検索とお気に入り一覧（Prisma）を同時に投げる（従来は検索 → お気に入りの2段直列）

**リポジトリ詳細のGitHub取得時間（実測）**

| リポジトリ     | リポジトリメタ | リリース一覧 | 直列（変更前） | 並列（変更後） | 差               |
| -------------- | -------------- | ------------ | -------------- | -------------- | ---------------- |
| vercel/next.js | 459 ms         | 2006 ms      | 2642 ms        | 2248 ms        | -394 ms (-14.9%) |
| facebook/react | 746 ms         | 1760 ms      | 2389 ms        | 1671 ms        | -718 ms (-30.0%) |
| prisma/prisma  | 407 ms         | 2284 ms      | 2669 ms        | 2507 ms        | -162 ms (-6.1%)  |

計測条件: 2026-07-28、`api.github.com` へPAT付きで直接リクエストし、直列（メタ → リリース）と
並列（`Promise.all`）を交互に7回ずつ実行した中央値。リリース一覧はアプリと同じ `per_page=100` ×
最大3ページ（`Link: rel="next"` を辿る）。

短縮量の理論値は「メタとリリースのうち短い方」＝リポジトリメタの所要時間（0.4〜0.7 s）で、
上表の差もその範囲に収まる。prisma/prisma で差が小さく出ているのは、リリース一覧側のばらつき
（1.6〜2.6 s）がメタの所要時間より大きく、中央値の比較でも吸収しきれないため。回線状況に依存する
数値なので、絶対値ではなく「メタ取得ぶんが critical path から消える」ことが本質。

**トレンドページ**

| 取得                                         | 中央値  |
| -------------------------------------------- | ------- |
| `GET /search/repositories`                   | 1005 ms |
| `favoriteRepo.findMany`（ローカルDocker DB） | 1.0 ms  |

ローカルDBは同一ホストのため短縮幅は1 ms程度だが、本番はSupabaseへのネットワーク往復になるため
その往復ぶんが検索の裏に隠れる。

**並列であることの自動検証**

E2Eのモックサーバーが `slow` で始まるownerへの応答を400 ms遅らせ、リクエストの開始・終了時刻を
記録する。`e2e/authed.spec.ts` の「リポジトリメタとリリースを同時に取得する」がその時刻から
「リリースの取得開始 < メタの応答完了」を検証しており、直列に戻すと落ちる（実際に直列へ戻して
落ちることを確認済み）。画面の表示時間ではなくリクエストの時刻で判定するため実行環境の速度に依存しない。

**再現方法**

各エンドポイントの所要時間を個別に測り、直列＝合計・並列＝最大として比較する。

```bash
curl -sS -o /dev/null -w 'repo %{time_total}\n' "https://api.github.com/repos/vercel/next.js"
curl -sS -o /dev/null -w 'releases %{time_total}\n' "https://api.github.com/repos/vercel/next.js/releases?per_page=100"
```

**本番での再計測**

2026-07-28 に本番 `/trending` を手動計測済み。Performance 99 → 100、LCP 2.1 s → 1.9 s、CLS 0.001 → 0。
数値と読み取りは上の「2026-07-28 の `/trending` 再計測（Issue #6 適用後）」を参照。
リポジトリ詳細（`/repos/:owner/:name`）はベースライン自体が無いため未計測。

## 計測の実施方法

### 未認証（CLI・自動）

Chromeがインストールされた環境で以下を実行する（Lighthouseのデフォルトがモバイルエミュレーション + Simulated throttling）。

```bash
npx lighthouse https://repo-radar-sigma.vercel.app/login \
  --output=json --output-path=./lh-login.json \
  --chrome-flags="--headless=new"
```

`/` と `/trending` もURLを変えて同様に実行する。結果のJSONから以下を読み取る:

- Performance スコア: `categories.performance.score`（×100）
- LCP: `audits['largest-contentful-paint'].displayValue`
- CLS: `audits['cumulative-layout-shift'].displayValue`
- TBT: `audits['total-blocking-time'].displayValue`

HTMLレポートで見たい場合は `--output=html` にする。

### 認証済み画面の計測手順（手動）

1. ChromeでGitHubログイン済みの状態で対象画面（`/` または `/trending`）を開く
2. DevTools → Lighthouse タブを開く
3. Device: **Mobile** / Categories: Performance を選択（Throttlingはデフォルトのまま）
4. 「Analyze page load」を実行し、Performance スコアと LCP / CLS / TBT を上の表に日付付きで追記する

シークレットウィンドウではセッションが無いためリダイレクトされる点に注意。通常ウィンドウで実行すると拡張機能が数値に影響しうるため、極端な値が出た場合は拡張機能を無効化したプロファイルで再計測する。

### フィールドデータ（実ユーザー計測）

`@vercel/speed-insights` / `@vercel/analytics` を導入済み（`src/app/layout.tsx`）。デプロイ後の実ユーザーのCore Web Vitalsは Vercelダッシュボード → 対象プロジェクト → **Speed Insights** で確認する（初回はダッシュボード側でEnableが必要。データ反映には訪問がある程度必要）。

## 記録のルール

- 再計測したら既存行を上書きせず、日付付きで新しいセクション（または行）を追加する
- 改善施策の前後で必ず同じ手順・同じ設定で計測する
